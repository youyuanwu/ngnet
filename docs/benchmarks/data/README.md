# Benchmark data

Measurements, filed by the machine that produced them. Criterion's own output under
`target/criterion/` is not committed — it is per-machine, large, and regenerated by the next
run — so what is kept here is a short markdown file per run: the conditions, the tables, and
what the run does and does not establish.

**Absolute figures from different machines must never be tabulated together.** Nothing here
is normalised for CPU model, kernel or io_uring implementation, and those are exactly the
variables the effects under study are sensitive to. What travels between machines is the shape
of a result — sign, relative magnitude against the drift controls of its own session, and the
mechanism advanced for it — which is what [`../findings/`](../findings/) records.

**No run recorded here compares `ngnet-qmux-h3` against anything.** Runs `01` to `03` predate the
cross-protocol arms entirely; `04` covers them but is a drift measurement, so its QMux figures are
the inputs to a variation calculation and not a comparison with the HTTP/2 arms beside them. The
HTTP/2 figures in `01` to `03` are still current — nothing about those arms changed when the QMux
ones were added, by design ([`../controls.md`](../controls.md)) — but a reader looking for a
cross-protocol number will not find one here, and should not infer one from the absence.

What `04` does give a reader is the bar: the socket QMux arm varies by **0.67%** on average and
the duplex one by **1.55%**, and `body_throughput/ngnet-qmux-h3/1048576` alone varies by
**10.42%**, which makes it the noisiest identifier in the suite and a poor place to look for a
small effect.

## Adding a run

1. Read [`../running.md`](../running.md) first, and in particular the five rules a run has to
   follow to be worth recording. A run that was not pinned, not interleaved and not controlled
   cannot be filed here, because it cannot be read later.
2. Copy the template and fill it in:

   ```sh
   cp docs/benchmarks/data/template/run.md \
      docs/benchmarks/data/<machine-id>/NN-<slug>.md
   ```

   `NN` is the next free two-digit number for that machine, so runs sort in the order they were
   taken. The slug names the question, not the answer.
3. Add a row to the run index above, and to the machine's own index.
4. If the run establishes or overturns something, say so in [`../findings/`](../findings/) and
   link back to the run. Keep the tables here; the finding quotes at most its headline figure.

## Adding a machine

```sh
mkdir docs/benchmarks/data/<machine-id>
cp docs/benchmarks/data/template/machine.md \
   docs/benchmarks/data/<machine-id>/README.md
```

The id is a short slug naming the hardware, not the person or the hostname — the point of the
directory is that a reader two years later can tell whether two numbers are comparable. Record
what was knowable at the time; a field that was never captured is written `not recorded`
rather than guessed. Then add the machine to the table above.

Before the first run on a new machine, check every arm can run there at all:

```sh
cargo bench -p ngnet-bench -- --test
```

The compio arms abort unless they obtain `DriverType::IoUring`, so this completing is also a
statement that io_uring is available.
